The seeder got past `swarm.join(discoveryKey, { server: true }).flushed()` (seed.js), so its announce
landed on the testnet. The probe joined the same discovery key as a client against the same
bootstrap and never saw a connection.

What this rules out, which the public-DHT attempts could not: the store is sound (the seeder read
it and reported the signed length), the key is right (both sides printed the same one), the build
is not at fault, and no NAT or home router is involved.

What it does not rule out: that the pair only ever works in one process. `test/seed-probe.js` runs
createTestnet, seed() and probe() inside a single process and passes, and that is the only place
replication has ever been observed working. Two processes is the untested configuration, and it is
the only one an operator uses.

Two dead ends worth not repeating, both hit on the way here:

1. The key in `results/publish.txt` (q6psfy7rz...) is from the key set that produced that committed
   log, not from a local `keys/`. Using it, seed.js and local-check.js both die with
   `Batch was not applied | Not supported operation in read only mode`. That is corestore trying to
   *create* a core for a key the store does not hold, which the `readOnly: true` both scripts pass
   forbids. The local key comes from the manifest over `keys/`, not from a results file.

2. That error says nothing about the actual problem. A key the store does not hold should say so.

## Correction, 2026-10-19, later the same day

**The conclusion above is wrong, and so is its headline.** Replication across two processes does
work: it was observed complete and correct. What this file originally recorded was a run against a
DHT that was not there.

Cause of the bad run: `pkill -f "scripts/testnet.js"` matches the shell invocation that contains
that string as well as the testnet, so the command that was meant to check whether the testnet was
alive killed it instead. The later `seed`/`probe` pair then talked to nothing. A bound UDP port was
read as evidence the testnet survived; it was not.

What a clean run produces, seeder and probe as separate processes over `scripts/testnet.js`:

```
seeding njz8wtxjwantpkjwd4s1fiwejroz64qjb5eorjrsdp14453c7hxo length 1076 byteLength 18253320
peer 66373b1b open, peers 1
peer 66373b1b close, peers 0
length 1076	peers 0	uploads 9	uploadBytes 114462

connect ms 7.8	update ms 5.2 blocks 0 bytes 0	core.length 1076
cold	26.9,75.8	ms 15.4	blocks 9	bytes 114462	zoom 14	tiles 4/4	address Kachi Basti, Sudarshanpura
repeat	26.9,75.8	ms 2.5	blocks 0	bytes 0	zoom 14	tiles 4/4
```

The seeder's `uploads 9 / uploadBytes 114462` equals the client's `blocks 9 / bytes 114462`, and
the repeat read costs nothing. That is the whole path working between two processes.

**What is still open, and it is not what this file first claimed.** The success above was the
first client a freshly started seeder served. Every client after it, and every client of a seeder
started later in the same session, connects — `connect ms` is 6-7 ms, so hyperswarm pairs them —
and then `core.update({ wait: true })` returns `core.length 0` after ~13 s having moved no bytes,
while the seeder logs no `peer ... open` at all. Six attempts across two seeder instances, with no
stale seeder and no second announcer on the discovery key.

Ruled out on the way, each by its own check:

- hyperswarm cross-process on this testnet: a bare server/client pair on an arbitrary topic, no
  maps-bee code in the path, connects every time.
- a discovery-key mismatch: the seeder's read-only store by key and a fresh client store by key
  produce the same discovery key, `965902ae5bd4dbc2...`.
- a stale seeder still announcing: `ps` showed exactly one seeder and one testnet.
- the store or the key: the seeder reads `length 1076` and prints it before announcing.

So the question is not "does replication work" but "why does a seeder serve one client and then
stop seeing peers". `label null` in these runs is unrelated and expected: `store/signed` holds
tiles only, no `g/` keys.

## Second correction, 2026-10-19: the "first client works" reading does not hold either

A clean run — nothing else running, fresh testnet, one `seed.js`, three sequential `probe.js` —
serves **none** of the three. The seeder logs no peer at all. So the earlier "first client is
served, the rest are not" was also contaminated: an instrumented seeder from a previous experiment
was still announcing the same discovery key, and clients were pairing with whichever announcer the
DHT handed them.

What the instrumentation did establish, each from a run with the identities printed on both sides:

- A client reports `connections 1` and names the seeder's own public key as the remote, while that
  seeder reports `connections 0` and never fires its `'connection'` handler. Both sides agree on
  the topic (`965902ae5bd4dbc2`).
- A plain hyperswarm server on the *same* discovery key, with a read-only Corestore open over
  `store/signed`, **does** fire its handler and does log the peer. So neither the topic nor the
  read-only store is the cause.
- The one difference between the server that fires and the server that does not is on the client:
  the working case had a client with no Corestore that never called `store.replicate(conn)`; the
  failing cases have a client that does.
- `test/seed-probe.js`, which runs the testnet, the seeder and the client in one process, passes
  on every suite run.

That is as far as measurement went. The mechanism is not identified, and the asymmetry — a client
holding a connection the server does not have — is more consistent with the transport than with
anything in this repo. This VM is a sandboxed Linux ARM64 container; two processes holepunching
UDX through a local DHT is exactly the path a sandbox is most likely to break, and in-process
replication working reliably here fits that.

**Next step is to run this on the Mac, not here.** `bare scripts/testnet.js`, then `seed.js` and
`probe.js` with `--bootstrap`, on real hardware. If it works there, this file is an environment
report and nothing more. If it fails there too, the instrumented pair that printed the identities
above is the way back in.
