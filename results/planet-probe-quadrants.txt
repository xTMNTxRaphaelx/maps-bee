## Four identical points, both builds, no prefetch. The variance is what collapsed.
#
#   point           2026-10-13              2026-10-16
#   26.9,75.8       266 blk / 10,157,879    198 blk / 1,561,851
#   51.5,-0.12      132 blk /  4,398,556     59 blk /   598,704
#   40.7,-74         19 blk /    442,189     50 blk /   463,375
#   -33.9,151.2      10 blk /    369,648     33 blk /   362,372
#   total           427 blk / 15,368,272    340 blk / 2,986,302
#
# 5.1x fewer bytes over the four. The gain is entirely in the expensive points: Jaipur 10.16 ->
# 1.56 MB and London 4.40 -> 0.60 MB, while New York and Sydney were already cheap and moved by
# a couple of percent. Every point now sits in a 0.36-1.56 MB band where the old build spread
# 0.37-10.16 MB, so the worst case improved 6.5x and the best barely moved. A preview no longer
# depends on whether its tiles happened to land in a fat block.
#
# Jaipur stays the outlier at 198 blocks only because it is first and pays the tree descent; the
# three after it cost 33-59 blocks and 0.36-0.60 MB. Read those as the steady-state figure and
# Jaipur as the cold-start one.
#
# The addresses also carry area parts the baseline could not produce at all — Westminster, Lower
# Manhattan, South Eveleigh — since it had no a/ gazetteer.

## Prefetch past one level costs more than it saves.
#
# Whole session, prefetch plus four cold previews:
#
#   levels   blocks        bytes
#   none        349     3,043,098
#   1           349     3,043,098
#   2           483     4,271,685
#   3         2,909    16,028,738
#
# Level 1 is exactly free, to the byte: its 17 blocks / 164,082 bytes are the root the first
# preview would have fetched anyway (198 blocks / 1,561,851 bytes becomes 17 + 181 and
# 164,082 + 1,397,769). It buys nothing and costs nothing, beyond moving ~200 ms of root fetch
# out of the first preview and into app start, which is worth having where the first preview is
# the one a user waits on.
#
# Level 2 runs 1.23 MB behind after four previews. It saves 1.29 MB on the first preview — the
# tree descent a cold client pays once — and then only ~83 KB each: Lugano 440 -> 290 KB, New
# York 612 -> 513 KB, Sydney 429 -> 429 KB unchanged. Break-even is near 18 previews in one
# session, which a chat client does not reach.
#
# Level 3 is 12.99 MB behind and saves ~99 KB per preview after the first: break-even near 125.
#
# app/ops.js ships PREFETCH_LEVELS = 2. On these numbers it should be 1.

## Against the 2026-10-13 baseline (results/planet-probe-2x2.txt), Jaipur 26.9,75.8, the one
## identical point between the two runs:

#   prefetch cost      1288 -> 315    47.95 MB -> 2.77 MB

# A cold first preview costs 6.5x fewer bytes than the old build while returning strictly more:
# the baseline had no a/ gazetteer and reported a city label only, where this returns the full
# three-part address. Blocks per preview went up and bytes went down because the blocks are
# smaller — 6.3 KB average here against 10.4 KB — so a preview no longer drags a ~40 KB block
# across the wire to read one tile. More round trips, far less waste; bytes per fetched lat/lon
# is the second design priority in CLAUDE.md, so that is the right direction.
